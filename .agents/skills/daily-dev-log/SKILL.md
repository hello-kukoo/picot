# 按日生成开发日志

从两个独立证据源恢复每天的真实工作：

1. Git commit log：确认已经落地并进入版本历史的变更。
2. Pi session 历史：补充调查、设计、测试、返工、用户反馈和未提交工作。

目标不是复述 commit message，而是把当天工作翻译成普通人能看懂的 2–3 条总结。每条说明“做了什么”“解决了什么问题”或“遇到了什么坑”。

## 默认约定

- 使用中文。
- 日期段含首尾，例如 `08-24 ~ 08-30` 包含 08-24 和 08-30。
- 默认按项目所在地或用户明确指定的时区归档；本仓库未指定时，默认使用 `Asia/Shanghai`。
- 默认只在回复中输出 Markdown，不创建文件、不提交、不推送。用户指定路径时才落盘。
- 每天 2–3 条，优先写用户能感知的功能、问题和结果。
- 没有证据的内容不写；没有记录的日期明确标注，不用相邻日期的工作填充。

## 工作流程

### 1. 先确认范围和工作树

先执行：

```bash
git status --short
git log -1 --date=iso-strict --pretty=fuller
```

保护已有未提交改动。开发日志是只读分析任务，不修改代码、不清理工作树、不重置文件。

确认：

- 日期起止日；
- 目标时区；
- 当前仓库根目录；
- session 目录是否存在；
- 用户要回复内容还是指定文件。

如果日期或时区会明显改变归档结果，先询问；否则采用默认约定，并在结果开头注明。

### 2. 提取 Git 证据

先获取宽范围 commit 数据，不要直接用带本地时区的 `--since/--until` 判断跨时区提交：

```bash
git log --all --date=iso-strict \
  --pretty=format:'%H%x09%aI%x09%an%x09%s' \
  --no-merges
```

将每条 commit 的 ISO 时间转换到目标时区，再按本地日期筛选。这样不会把 `+0000`、`-0700` 和 `+0800` 的提交错放到相邻日期。

对筛选出的 commit：

- 保留短 hash、日期、作者和标题作为追溯信息；
- 用 `git show --stat --summary <hash>` 看实际影响范围；
- 对高影响或标题含义不清的 commit，再读必要的 diff；
- 合并提交通常不计为独立开发，除非它包含无法从其他 commit 判断的实际工作；
- 自动升级、依赖升级、格式化等只在确实影响用户或发布流程时写入；
- 不把 commit 标题直接当作功能证明。

大 commit 不必完整输出 diff。先看 stat 和关键文件，再提炼用户可感知结果。文件名、测试名和内部模块名只作为证据，不直接塞进面向用户的日志。

### 3. 提取 Pi session 证据

默认 session 目录：

```text
~/.pi/agent/sessions/--<当前仓库绝对路径编码>--/
```

当前仓库路径不确定时，用实际 `pwd` 和目录列表确认，不凭记忆拼路径。读取日期段附近的 `.jsonl` 和必要的 `.jsonl.exit` 文件；不要把整个 JSONL 原样倾倒到对话中。

提取并归纳：

- 用户提出的目标和验收标准；
- 实际查看、修改、测试和提交的内容；
- bug 复现、根因和修复；
- 被否决的方案和最终取舍；
- 测试结果、人工验证结果和未完成事项；
- 明确的“未提交”“未 push”“待用户确认”等状态。

过滤噪声：

- 跳过 subagent session：根文件中带 `parentSession` 的记录，以及子目录中的 session；
- 忽略工具调用的重复过程，只保留能改变结论的事实；
- 不公开 token、密码、个人隐私或完整环境信息；
- 不把助手的计划当成完成结果；
- 用户反馈优先于助手的早期推测，但最终状态必须以实际验证或 commit 为准。

当 session 内容很多时，在本地脚本中做筛选和摘要，只把结论带回上下文。优先保留用户消息、最终总结、错误信息和测试结果，不要把数百 KB 原始日志全部读入对话。

### 4. 按本地日期合并

为每个日期建立事实清单，合并 Git 和 session：

| 事实类型 | 写法 | 证据要求 |
| --- | --- | --- |
| 已完成功能 | “增加……，用户现在可以……” | commit 或 session 的完成与验证 |
| 问题修复 | “发现……，后来改为……” | session 的复现/根因/修复，最好有 commit |
| 调查或设计 | “梳理……，确定……” | session 中有明确结论；不能写成已上线 |
| 测试验证 | “验证……可用” | 明确测试、人工复现或发布检查结果 |
| 未完成事项 | “仍待……” | session 或 commit 明确留下 |
| 自动化工作 | “系统自动升级……” | bot commit；注明不是人工开发 |

处理重复：

- 同一功能在多个 commit 或多个 session 中出现时合并成一条；
- 同一 bug 的“发现—定位—修复—验证”写成一条完整故事；
- 同一天内容很多时，优先级为：用户功能 > 重要问题 > 发布/稳定性 > 纯整理；
- 一个主题跨多天时，按当天实际进展拆开，不在每天重复完整背景。

处理冲突：

- commit 已提交但 session 说“未提交”：按时间顺序核对，不能直接选一边；
- session 说“完成”但没有代码、测试或提交证据：写成“完成调查/准备”，不要写成已交付功能；
- commit 标题与 diff 不一致：以 diff 和实际验证为准；
- 无法解决的冲突在日志中简短注明，不能自行补全。

### 5. 翻译成非技术语言

把内部术语转成用户能理解的表达：

- `feat: add ...` → “增加……功能，用户可以……”；
- `refactor` → “整理并简化……，降低后续维护风险”；
- `cache invalidation` → “登录状态变化后清掉旧数据，避免页面显示过期信息”；
- `broker / token / OIDC` → “由 Picot 统一管理登录凭据/公司身份验证”，只有影响用户理解时才保留术语；
- `race condition` → “两个操作同时发生时，后一个操作可能被忽略”；
- `migration` → “把原有能力迁入当前版本”；
- `test suite` → “补充检查，确认主要流程没有被改坏”。

避免：

- 大段技术名词、文件路径、模块名和代码；
- 直接罗列 commit 标题；
- 只写“优化、完善、重构”而不说具体改变；
- 把测试数量当作主要成果；
- 用夸张的“全面解决”“完全稳定”等无法证明的表述。

### 6. 输出前润色

完成事实归纳和非技术化改写后，调用 `skill:humanizer-zh` 对整篇日志润色，再交付给用户。目标是去掉 AI 写作痕迹，让文字像真实开发记录，不是重新生成内容。

重点检查并按需改写：

- 破折号堆砌、否定式排比和机械的三段式表达；
- “此外”“另外”“与此同时”等不必要的连接词；
- 宣传性语言、空泛的“优化/提升/完善”和口号式收尾；
- 模糊归因、过度限定和重复句式；
- 机械的粗体小标题、整齐但僵硬的句子结构。

润色时必须保留：

- 日期、目标时区和日期归档结果；
- 每条事实的证据依据；
- “已完成”“仅调查”“未提交”“自动化任务”等状态区别；
- 没有记录日期的明确说明；
- 面向非技术读者的要求，不能把已删除的术语重新加回来；
- 文末追溯信息中的 commit hash 和文件路径。

如果用户指定了简洁、叙事或其他写作风格，以用户要求为准。Humanizer 只能调整表达，不能改变事实、证据等级或完成状态。

## 输出格式

默认使用以下结构：

```md
按[时区]整理，日期含首尾。

## 08-24

- [功能或进展]。
- [问题或踩坑，以及处理结果]。

## 08-25

- [功能或进展]。
- [验证、整理或遗留问题]。

## 08-26

- [当天总结]。
- [当天坑点或结果]。
```

每个有记录的日期写 2–3 条。当天只有一个小改动时写 1–2 条，不强行凑数。

没有人工开发记录时，明确写：

```md
## 08-30

- 没有新的人工开发记录。
- 自动化流程完成……（如果当天确有 bot 或 CI 记录）。
```

如果用户需要追溯，再在文末追加简短的“来源范围”，只列日期和 commit hash；默认不列文件清单和内部实现细节。

## 完成前核对

- [ ] 日期段首尾都覆盖；日期按目标时区归档；
- [ ] 每条结论能追溯到 Git 或 session；
- [ ] 区分已完成、调查、计划、自动化任务和未完成；
- [ ] 没有把 merge、计划或早期推测误写成新功能；
- [ ] 每天控制在 2–3 条，普通读者能看懂；
- [ ] 真实 bug 写清“现象—原因—处理”，不只写“已修复”；
- [ ] 已通过 `skill:humanizer-zh` 润色，且没有改变事实、证据和状态；
- [ ] 无记录日期没有用邻近日子内容填充；
- [ ] 没有泄露凭据、隐私或大段原始 session；
- [ ] 用户指定落盘时，检查文件内容和 diff；否则只回复，不创建文件。

## 边界

本 skill 只负责从 Git 和 Pi session 生成开发日志。它不负责修改产品代码、修复发现的 bug、提交或推送代码，也不把日志写入项目文件，除非用户明确指定输出路径。
